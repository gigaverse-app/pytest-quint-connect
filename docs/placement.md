# Where contracts live

A contract is a model, a manifest, a driver and a test. Where you put them decides whether a reader
can find the contract from the code it models, whether it runs in CI, and whether it ships by
accident. This page gives the layouts that work and the rules behind them.

## Rules that hold in every layout

- **One directory per contract.** The model, `quint-connect.json`, the generated driver base, the
  driver (`conftest.py`), the test module, a README, and `history/` for frozen evidence all sit
  together. A reader opens one directory and has the whole contract.
- **Outside the main test run.** Contracts run through their own configuration
  (`pytest -c contracts/quint.ini contracts`). The main run must not collect them: set `testpaths`,
  add `contracts` to `norecursedirs`, or pass `--ignore=contracts` (see [CI](ci.md#keep-contracts-out-of-the-main-suite)).
- **Outside what ships.** A driver is test code: it imports the code under test, may monkeypatch
  it, and may execute frozen copies of old code. Keep contracts out of wheels and images. A wheel
  that packages only `src/` is safe by default. A container that copies the whole repository
  (`COPY . /app`) needs `contracts` in `.dockerignore`.
- **Linked in both directions.** The manifest's `sources` point from the contract to the code.
  Point back with one line in the modelled class's or function's docstring:

  ```python
  class InMemoryOwner:
      """
      ...
      Contract: contracts/pytest_obligation/references/in_memory/fenced_lease/ replays Quint
      histories against this class. Change it and the model in the same pull request.
      """
  ```

- **Frozen evidence in `history/`.** An audit model that found a bug and the shipped pre-fix code a
  [found bug's mutant](manifest.md#bugs-found) runs never change; pin them by SHA-256 so they
  cannot be edited until they agree with the model.

## Choose a layout

### Flat: `contracts/<behavior>/`

The default, and the one the [tutorial](tutorial.md) and the [agent skill](../skills/pytest-quint-connect/SKILL.md)
use. Best for a library or a handful of contracts.

```text
contracts/
├── quint.ini
├── lru_cache/
└── session_receipts/
```

Name each directory after the behavior (`lru_cache`, `mutable_bidict`), never after the package
under test: anywhere `contracts/` is on an import path, a directory named `bidict` can shadow the
real `bidict`.

### Mirrored: `contracts/<import path of the modelled module>/<behavior>/`

Best once a codebase has several contracts across packages or services: the path itself says what
each contract models, and a reviewer of `refunds.py` knows where to look.

```text
package/src/pytest_obligation/references/in_memory.py      the modelled code
contracts/
├── README.md                                              index: contract, modelled code, bugs found
├── quint.ini
└── pytest_obligation/references/in_memory/fenced_lease/
    ├── README.md                 what it models and why, the rule, a diagram, the bug it found
    ├── model.qnt
    ├── quint-connect.json
    ├── fenced_lease_driver.py    generated by codegen; never edited
    ├── conftest.py               the driver, subclassing the generated base
    ├── test_fenced_lease_contract.py
    └── history/
```

Mirroring puts a directory named after your package (`contracts/pytest_obligation/`) inside
`contracts/`, so the shadowing rule becomes strict:

- **Never put `contracts/` itself on an import path**: not in `pythonpath`, not in a type checker's
  search path. Point `pythonpath` at your source directory (`../src`) instead.
- **Keep pytest's default import mode.** It puts each contract's own directory on `sys.path` (so its
  `conftest.py` can import the generated base beside it), not `contracts/`. `--import-mode=importlib`
  does neither, and the generated base cannot be imported.
- **Give every test and driver module a unique name** (`test_<behavior>_contract.py`,
  `<behavior>_driver.py`): under the default import mode, two modules with one name collide.
- **Add [`attest`](manifest.md)** so a run that imported the wrong copy of the package fails.

`pytest -c contracts/quint.ini contracts` then runs every contract, with node ids relative to
`contracts/` when `quint.ini` sets `--rootdir=contracts`.

### In practice

| Repository | Layout | Watch for |
| --- | --- | --- |
| A library with `src/` | Flat or mirrored at the repository root | `pythonpath = ../src` in `contracts/quint.ini` |
| A monorepo of services (`src/<org>/<service>/`) | Mirrored: `contracts/<org>/<service>/<module>/<behavior>/` | A driver models one service; cross-service contracts belong with shared code. Route `contracts/<org>/<service>/**` to that service's CI lane |
| A Django project (apps under one package, no `testpaths`) | Mirrored: `contracts/<project>/<app>/<module>/<behavior>/` | Add `contracts` to `norecursedirs`; set the settings module in `quint.ini`; driver fixtures can use the database fixtures as usual |

## Make the contract readable

A model only protects the code if reviewers can tell what it claims.

- **Open the model with a header**: what it models (file and class), why it matters, what it
  covers, what it does **not** cover, and when to update it. The "not covered" line is what stops
  the model from being over-trusted.
- **Note on each action the real call it drives**, mark the rule with `// @invariant` and one
  sentence on why it matters, and keep a one-line catalog of the witnesses.
- **Give each contract a README** that opens with three plain sentences: what the code does, the
  rule, and any bug the contract found. Follow them with a diagram. GitHub renders Mermaid, so a
  state diagram costs a few lines:

  ````markdown
  ```mermaid
  stateDiagram-v2
      [*] --> READY
      READY --> CLAIMED: claim
      CLAIMED --> READY: reaper, lease expired
  ```
  ````

  Put the same diagram in the pull request that adds the contract. The PR comment's "What the
  contract says" section lists the actions and a witness step by step.

## Learn to model

These pages cover connecting a model to Python. For writing the model itself, the skills in
[quint-llm-kit](https://github.com/quint-co/quint-llm-kit/tree/main/quint-llm-kit-plugin/skills)
go deeper:

- [`quint-modeling`](https://github.com/quint-co/quint-llm-kit/tree/main/quint-llm-kit-plugin/skills/quint-modeling):
  building a spec from requirements or from existing code, a review checklist, and the handoff
  notes (what it covers, what it does not, when to update it).
- [`quint-lang`](https://github.com/quint-co/quint-llm-kit/tree/main/quint-llm-kit-plugin/skills/quint-lang):
  the language and CLI, including witnesses and test files.
- [`quint-execute-spec`](https://github.com/quint-co/quint-llm-kit/tree/main/quint-llm-kit-plugin/skills/quint-execute-spec):
  a loop for changing code with the spec as the guide.

quint-llm-kit keeps specs in `specs/` and its own model-to-code connection targets Rust. Use its
modelling guidance with this plugin's layout and drivers.
